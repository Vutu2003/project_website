# Frontend

## Stack

React 19 + TypeScript 5 + Vite 7, React Router 7 in declarative SPA mode, native `fetch`, CSS. Node 24.21.0/npm 11.19.0 were selected through the project toolchain for Phase 4.1. `package-lock.json` pins resolved dependencies.

## Prerequisites

Start from the repository root on Linux/Bash. PostgreSQL 16 and the frozen Spring Boot backend must be available. Node/npm are already in `.toolchain/node`; use `source scripts/use-toolchain.sh` in each terminal.

## Environment

Copy `frontend/.env.example` to `frontend/.env` only if changing the API URL. Default: `VITE_API_BASE_URL=http://localhost:8080`. The backend accepts exactly `FRONTEND_ORIGIN=http://localhost:5173` by default. Keep the browser at **localhost:5173** so its origin matches; Vite binds to loopback. Neither file contains secrets. For another origin, set `FRONTEND_ORIGIN` before starting backend and align the browser URL. Restart Vite after changing its environment file.

## Install

```bash
source scripts/use-toolchain.sh
npm install --prefix frontend
```

## Run Backend

Follow [backend/README.md](../backend/README.md) to start the project-owned PostgreSQL cluster, migrate/seed an empty backend database if needed, and bootstrap demo login hashes. For an already seeded dev database:

```bash
source scripts/use-toolchain.sh
./backend/scripts/setup-dev-db.sh
source .local-postgres/backend-dev.env
source .local-postgres/backend-security.env
env -u DEBUG mvn -f backend/pom.xml spring-boot:run
```

Check `http://localhost:8080/actuator/health` for `UP`. Do not print or commit the generated password/JWT environment values.

## Run Frontend

In a second terminal:

```bash
source scripts/use-toolchain.sh
npm run dev --prefix frontend
```

Open **http://localhost:5173/login**. Vite listens on loopback port 5173; the build uses direct browser calls to the real backend at port 8080.

## Login

Use a local demo account: `demo_vtyt`, `demo_bgd`, `demo_khoa_noi`, or `demo_admin`. Their passwords are generated by `./backend/scripts/setup-demo-login.sh` into ignored `.local-postgres/backend-security.env`; no password is embedded in the UI or this README. The login form sends `POST /api/auth/login`, then verifies the returned Bearer token through `GET /api/auth/me`.

## Build

```bash
npm run build --prefix frontend
```

TypeScript checks strict application types before Vite writes ignored `frontend/dist/`.

## Lint/Test

```bash
npm run lint --prefix frontend
npm run test --prefix frontend
```

Vitest checks session storage, Bearer header injection, backend error normalization, expired-token cleanup, network failure, workflow labels, 409 feedback and typed workflow requests. Real Chrome browser smoke remains the integration baseline.

## Project Structure

- `src/api`: typed `fetch` client, auth/workflow endpoints and normalized errors.
- `src/auth`: session storage, context, restore/logout and route guards.
- `src/components`: loading, pagination, workflow feedback/status badges and render error boundary.
- `src/layouts`, `src/routes`: app shell and role-aware navigation configuration.
- `src/pages`: login, dashboard, plan/approval/execution/handover/report/history pages, unauthorized and 404 pages.
- `src/types`, `src/utils`: exact backend roles/workflow DTOs and Vietnamese labels.
- `src/styles.css`: small responsive visual foundation.

## Authentication Flow

This is a **single-page application (SPA)**: React updates the view in the browser without loading a new HTML document on each route. React Router maps browser paths to pages. A protected route waits for session initialization before showing the shell. Login obtains a backend JWT; the central API client sends it as `Authorization: Bearer ...`. On refresh, the app reads the token from `sessionStorage`, calls `/api/auth/me`, and trusts the returned current identity. Invalid/expired tokens are removed and lead to login. Logout clears the local token/user; the backend has no logout endpoint or refresh token.

`sessionStorage` keeps the token for one browser tab across refresh and discards it when that tab closes. It is readable by JavaScript on the page, so an XSS bug could steal it. This is a pragmatic local demo choice, not a replacement for production browser security review. No password or token is intentionally logged. Role-aware menus and `RoleGuard` only improve UX; backend authorization is authoritative.

## Phase 4.2 Screens

`/plans` lists real plans for authenticated users. PHONG_VTYT can use `/plans/new`, `/plans/:planId` and `/plans/:planId/edit`; BAN_GIAM_DOC uses `/approvals` and `/approvals/:requestId`. Plan detail is readable by authenticated roles, with only VTYT command controls. Execution/handover are available from Phase 4.3; report/history are available from Phase 4.4. See the [workflow guide](docs/planning-provider-ui.md).

## Planning Workflow

Create from paged active equipment, edit DRAFT/REVISION_REQUIRED plans while retaining existing items, then submit a DRAFT plan for director review. Dates are ISO `YYYY-MM-DD`; the browser checks simple form quality and the backend decides eligibility and transitions. Each versioned write uses the loaded server version. The list and item table use backend pagination.

## Approval Workflow

A BAN_GIAM_DOC user opens the real pending queue, inspects the plan or vendor proposal and chooses approve or revision with a reason. The queue refreshes after a decision. Plan revision can be edited back to DRAFT, submitted again and reviewed in a new approval round.

## Provider Routing Workflow

On an APPROVED plan, PHONG_VTYT selects an explicit verified coverage row. FREE routes to UNDER_CONTRACT with the backend-selected provider. NOT_FREE routes to PENDING_PROPOSAL; VTYT can save, reopen after refresh and submit an external-provider proposal. The director then approves or requests a new proposal round. UNKNOWN and missing coverage do not provide a selectable route.

## Conflict Handling

`OPTIMISTIC_LOCK_CONFLICT` (409) shows a specific message and reload action. Reload displays current server data; the browser never silently retries a stale write. Other business 409 responses preserve the backend message. 401 uses the Phase 4.1 session flow; 403 and 404 have distinct feedback.

## Phase 4.3 Screens

PHONG_VTYT and KHOA_PHONG open `/execution`, select a plan at `/execution/plans/:planId`, then open `/plans/:planId/items/:itemId/execution`. Plan detail also links relevant items. The item page displays actual provider, every execution attempt, progress, technical and handover evidence, and only the current role/state's controls. See the [execution guide](docs/execution-acceptance-ui.md).

## Execution Workflow

VTYT starts a routed or rework item with both item and plan versions. The backend assigns attempt number and provider. The browser reloads stored plan/item/attempts after every command. First start may move the plan to IN_PROGRESS.

## Progress Logging

Append a work note and optional damage note on the current active attempt. Prior logs and attempts are read-only. Each log displays its server timestamp and recorder ID; there is no edit/delete control.

## Technical Acceptance

After VTYT ends work, technical PASS moves the current attempt toward handover. FAIL records a conclusion and chooses rework or repair hand-off. The conclusion and result remain attached to that exact attempt.

## Rework

A REWORK_REQUIRED item can start a new attempt. The page displays every prior failed attempt and the latest attempt separately. An old technical PASS cannot unlock handover on the new attempt.

## Repair Hand-off

An active attempt can be handed to repair with a required reason; technical/handover FAIL may also choose repair. REPAIR_REQUIRED is terminal in V1. The UI retains evidence and offers no restart or repair subsystem.

## Handover

A KHOA_PHONG account sees only the plans/items allowed by the backend's historical department scope. Handover is offered only on the current attempt after technical PASS. PASS completes the item; FAIL requests rework or repair. When all items are terminal, the plan may show AWAITING_REPORT; VTYT can open the UC11 report page.

## Two-signer Authentication

Handover PASS requires a second PHONG_VTYT username/password. The browser obtains a temporary token through `/api/auth/login` and sends it only in `X-VTYT-Authorization`, while the primary KHOA token stays in `Authorization`. The second token is never placed in browser storage or UI; the credentials are cleared after the attempt. Handover FAIL does not require the second signer.

## Multi-attempt UI

The current execution is labelled; old attempts show their own provider, start/end, progress, technical and handover evidence and cannot be edited. The page reads the scoped existing equipment-history projection and selects the matching plan item. The full UC12 equipment-history UI now uses the same projection and attempt component.

## Phase 4.3 Conflict Handling

A stale item/plan version returns 409 with a reload action and no silent retry. Local input messages are explicit; unexpected JavaScript details are hidden. Busy buttons and an immediate in-flight guard prevent duplicate clicks; the backend remains the final duplicate and role guard.

## Reporting

VTYT filters AWAITING_REPORT plans, creates/edits one DRAFT and finalizes it. BGD reads reports. FINAL is read-only. The page separates COMPLETED and REPAIR_REQUIRED counts and reloads backend state after every write. Stale versions and duplicate creates show safe 409 feedback. No CLOSED command is offered.

## Equipment History

The equipment list uses the backend scope and includes inactive equipment. One history GET renders all returned campaigns, all attempts and progress, failed technical/handover evidence, status chronology and concise report references. KHOA_PHONG sees only its historical campaigns. The [frontend freeze](docs/frontend-v1-freeze.md) records the V1 contract.
